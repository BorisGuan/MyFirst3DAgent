# Portfolio Summary

I built a controlled 3D model modification agent architecture for Blender-focused hard-surface and mecha design workflows. The project is not a simple chatbot that writes Blender Python. It is a state-based agent execution system that translates natural language design requests into structured task state, plans against a registry of safe domain operations, dispatches deterministic handlers, and isolates Blender `bpy` access behind a Core API boundary.

The main problem I wanted to solve is that naive LLM scripting is risky in production-like 3D workflows. If an LLM directly generates Blender scripts, the system can overwrite source files, call unexpected APIs, perform destructive mesh edits, or produce behavior that is difficult to test and audit. Also, user intent such as "add mechanical detail to the chest armor" is not equivalent to a Blender API call. A real modeling assistant needs a translation layer: natural language should become a controlled design action with a known target, known parameters, known safety policy, known persistence behavior, and a structured report.

The central architecture choice is `TaskObject` as the single source of truth. `TaskObject` carries the user input, semantic target, intent, constraints, planning result, runtime paths, result summary, diagnostics, and artifacts. It moves through an explicit lifecycle: `draft`, `validated`, `bound`, `planned`, `ready_to_execute`, `executing`, and finally `completed` or `failed`. The project also includes ownership rules that define which layer may modify which fields. The Agent Layer can create the draft. Planning can bind targets and select operations. Runtime can record execution and results. Domain operations cannot mutate the task at all. This prevents the common agent-system failure mode where planning facts, execution facts, and tool results drift into separate sources of truth.

The execution pipeline is deliberately layered. The Agent Layer receives natural language, uses context summaries, and creates a draft task. Planning validates the task, maps the semantic part to a Blender object using scene/binding context, selects an operation through `OperationRegistry`, completes parameters from `OperationSpec`, and checks a safe non-destructive policy. Runtime only accepts `ready_to_execute` tasks. It derives a minimal `DomainOperationInput`, dispatches a registered domain handler, coordinates saving an output `.blend` copy, writes a Runtime report, and marks the task completed or failed. Domain handlers implement fixed design operations such as `edge_soften`, `panel_line_bevel_prepare`, `thruster_nozzle_prepare`, and `weighted_normal_finish`. They call Core API helpers such as `add_bevel_modifier`, `add_solidify_modifier`, and `add_weighted_normal_modifier`. Core API is the only layer that touches Blender `bpy`.

This is safer and more scalable than naive LLM scripting because the LLM is not the executor. It cannot invent arbitrary `bpy` calls at execution time. The executable surface is the operation registry. The system currently has ten modifier-only, non-destructive atomic operations in Atomic Operation Library v1. They form a small domain-specific operation language for mecha modeling: surface/panel operations, form/mass preview operations, functional detail operations, and finish operations. These operations are reusable and composable later, but the project intentionally avoids premature sequence/composite abstraction until enough real usage patterns justify it.

A major technical highlight is the evaluation mindset. The repository includes unit tests for TaskObject schema, lifecycle, ownership, Agent draft creation, Planning stages, OperationSpec/OperationRegistry, DomainOperationInput, Runtime execution, Domain handlers, Core API helpers, CLI flow, reporting, and fake end-to-end execution. The current suite reports 366 passing tests. There is also a manual real Blender smoke runner that enters through a serialized TaskObject and verifies that an output `.blend` copy and Runtime report are produced while the source file remains unchanged.

The current limitations are clear and intentional. Parameter accuracy still needs work: `style`, `density`, `scale`, and degree words are captured in intent but are not yet fully mapped to operation-specific parameter profiles. Target binding confidence exists in the binding context but is not yet a first-class TaskObject field. Runtime reports are structured but do not yet feed back into future planning. Real Blender smoke coverage currently focuses on `edge_soften`, and composite operations are postponed.

The next phase I would prioritize is architecture-level optimization before adding more features: operation parameter accuracy analysis, operation selection accuracy review, target binding confidence/user confirmation, Runtime preflight and post-check, report-to-planning feedback, and a real Blender smoke matrix across all atomic operations. This shows the main engineering principle behind the project: grow agent capability through controlled contracts, explicit state, safety boundaries, and evaluation rather than through unconstrained tool use.
